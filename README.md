# ServerSync 1.1.2

为 Minecraft **1.21.1 / NeoForge 21.1.219 及以上 21.1.x / Java 21+** 编写的双端模组。

玩家点击加入服务器时，自动从**当前连接的服务器地址及游戏端口**读取被监控模组清单，按 **SHA-256** 比较文件内容，下载不同的 jar，提示退出并重启。独立 Java 更新程序等待游戏进程退出后备份旧文件、替换文件。下一次启动重新校验，通过后才连接服务器。服务端在配置阶段再次检查客户端确认结果。

**直接读取服务端 `mods` 文件夹；服务端配置只写监控列表；下载与游戏共用一个 TCP 端口；客户端无需填写同步地址。**

**第一次必须在服务端和每位玩家客户端手动安装 ServerSync。** 原版客户端或未安装此模组的客户端不能由服务端直接写入文件。已经加载的模组不能热替换；必须完全退出游戏再启动，返回主菜单不算重启。

## 服务端部署

1. 关闭服务器，把 `serversync-1.1.2.jar` 放进服务器 `mods`。
2. 启动一次，生成 `config/serversync-server.properties`。默认同步 `create_mobile_packages`，服务器未安装它时会报错，需要先修改清单。
3. 编辑配置，列出需要客户端保持一致的**双端模组 ID**（不是文件名）：

```properties
modIds=create_mobile_packages
```

多个模组例如 `modIds=create_mobile_packages,create`。依赖也需要同步时应显式加入清单。只同步清单内模组，不会删除玩家的光影、地图等其他客户端模组。不应把专用服务端模组加入清单。一个 jar 含多个 mod ID 时，在清单中选其中一个 ID 即可，不能重复列出同一个 jar。

4. 重启服务器。**只需原有游戏 TCP 端口**：自动共用 `server.properties` 中的 `server-port` 和绑定地址，无需再开放下载端口。例如游戏端口 `25565`，下载也使用 `25565`；改成 `30123` 后两者一起使用 `30123`。
5. 浏览器打开 `http://服务器地址:游戏端口/manifest` 应看到 `serversync-1` 和模组哈希清单。HTTP 请求在 Minecraft 数据包解码之前分流；游戏握手继续使用原网络处理流程。

旧版配置中的 `bind`、`port` 字段已废弃并忽略，可以删除。更新到 1.1.2 时，服务端和所有客户端都需要手动替换 ServerSync 本身的旧 jar。

每次更新流程：**关闭服务器 → 替换服务器 mods 中的 jar 并移走旧版本 → 启动服务器**。启动时生成不可变的分发快照，不需要单独维护另一份更新 jar。游戏运行时只替换服务器磁盘文件不会发布新版本，因为服务器内存仍运行旧代码。

## 客户端部署（每位玩家仅配置一次）

1. 在与服务器相同的游戏版本和 NeoForge 环境中安装 `serversync-1.1.2.jar`。
2. 正常在多人服务器列表输入服务器地址并点击加入，**无需客户端配置文件或单独同步地址**。域名和 SRV 记录按 Minecraft 自身的解析结果选择实际服务器地址和端口。旧版 `serversync-client.properties` 已不再读取，可以删除。
3. 匹配则进入正常连接过程；不匹配则显示下载状态，下载完成后点击 **退出游戏并应用更新**。
4. 等待 `serversync-client/updater.log` 出现 `SUCCESS`（通常数秒），再通过原来的启动器启动游戏并加入。不会保存启动器密码或自动重启启动器。

普通服务器不支持同步接口时继续正常连接；装有 ServerSync 的服务器仍会通过配置阶段的第二次校验拒绝不一致客户端。若获取清单失败而回退到游戏连接，将无法自动更新缺失模组，加载器或校验关卡会拒绝不一致的客户端。

## 更新与恢复

- 下载和暂存目录：`serversync-client/stage-*`。
- 旧 jar 备份：`serversync-client/backup-*`。旧版本文件名不同也会按 mod ID 找到并移走，避免同一模组出现两个版本。
- 校验失败、下载失败或文件冲突时阻止连接，已经安装的 jar 保持不变。
- 应用更新时遇到普通文件操作错误会尝试回滚，失败记录在 `updater.log`；断电或强制杀死更新程序可能需要手动恢复备份。
- `pending` 存在或游戏在更新完成前启动时禁止入服，避免本次进程仍加载旧代码。
- 更新失败后：关闭游戏，检查日志并修复权限/占用问题。可以在游戏目录执行 `java -cp serversync-client/updater.jar cn.serversync.UpdateHelper --apply .` 重试。不要在游戏运行期间手动执行。
- 如需手动恢复，关闭游戏和更新程序，按备份恢复原 jar，再移走 `pending`，然后重新启动并同步。暂存及备份不会自动清理，以便排查；确认运行正常后可删除旧目录。
- ServerSync 本身、Minecraft 和 NeoForge 的更新需要管理员另行发放；不通过这个机制自更新。

## 信任与边界

客户端会自动下载当前连接服务器提供的**可执行 Java 模组代码**，因此应仅连接信任的服务器。共用游戏端口的下载接口是 HTTP，不自带 TLS 或身份验证；SHA-256 用于文件一致性和完整性检查，不能证明服务器来源。接口仅分发监控列表内的模组快照，不提供世界、配置或任意路径下载。

直接连接专用服务器、路由器端口映射、原样转发 TCP 的穿透可共用一个端口。Velocity/Bungee 等解析 Minecraft 协议的代理不会自动转发 HTTP：这类架构还需要在同一公网端口上配置协议分流，不能只把模组放在代理后端。不能额外要求客户端填写下载端口。

这是正常玩家的更新和一致性工具，**不是反作弊或远程可信证明**：恶意修改过的客户端可以伪造协议回复。不会禁止所有额外客户端模组，只要求配置范围内文件一致。jar 内的模组描述需要常规 `[[mods]]` / `modId="..."` 格式；不支持 Fabric、嵌套 jar 单独同步或复杂 TOML 动态标识。

## 构建与验证

使用 JDK 21+，Windows：先将当前终端的 `JAVA_HOME` 设为 JDK 21 或更高版本的安装目录，再运行 `gradlew.bat build`。Gradle 可自动准备 Java 21 编译工具链。模组输出为 `build/libs/serversync-1.1.2.jar`。

集成测试覆盖同版本号不同内容、重复版本、改名替换、客户端模组保留、备份、损坏文件、清单越界、HTTP 快照、截断下载、独立更新进程，以及同一 TCP 端口上的游戏字节透传、分片 HTTP 请求和自定义端口/IPv6 地址。实际 Minecraft Mixin 注入、双端联机、渲染、SRV 和 Windows 游戏进程退出后 jar 解锁仍需按 `MANUAL_QA.md` 实测。

1.1.2 修复了 Mixin 包隔离错误和 `[[mods]] #mandatory` 注释表头识别问题。14 项测试通过；已在 Linux / NeoForge 21.1.233 的真实服务器上验证启动、同端口模组下载（SHA-256 一致）和 Minecraft 状态握手。玩家完整入服、客户端界面、SRV 与 Windows 退出更新仍需验收。
